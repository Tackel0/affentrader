# Saved Pine-script alerts

The Alerts manager has a **Pine Script** creation tab. Choose the current editor draft, an installed Pine study or the EMA example; load the inputs and alert conditions; select a named `alertcondition()`, **Any alert() function call**, **Order fills only** or **Order fills and alert() function calls**; then save. Fill options require a strategy. Editing the chart or indicator afterward does not update the saved script. Editing an alert retains its script snapshot; create another subscription to change the code, inputs, libraries, market or interval.

## Execution and persistence

Each symbol has an independent PineTS 0.13.0 context inside a QuickJS interpreter. Browser execution runs in a dedicated worker; server execution runs the same generated runtime and interpreter. Source, primitive inputs, imported `Author/Library/Version` source bodies, history depth, chart type and display timezone are copied when the subscription is created. The generated runtime is built reproducibly from the existing source-checked strategy runtime; package files are not modified.

Historical warm-up never emits notifications. Subsequent observations evaluate the live tail and finalize an observed previous candle before its successor. Intrabar state, including `varip`, lives in that subscription's interpreter. Browser trade identifiers distinguish real observations with identical OHLCV from duplicate polls. By default, strategy calculations run on confirmed candles; `calc_on_every_tick=true` enables observed intrabar calculations and `calc_on_order_fills=true` enables fill recalculations. Pending broker orders can execute at live observations independently of those calculation settings.

Named indicator conditions use the chosen alert timing policy. `alert()` calls use the frequency in the script, with one shared per-bar call gate for `freq_once_per_bar` and `freq_once_per_bar_close`; `freq_all` can emit multiple events. Durable gates and committed events are stored together with rate counters, last firing times, per-member completion and a journal delivery cursor. Restarting a stopped watchlist member leaves other members' run identities and live contexts intact.

Messages support symbol, exchange, interval, time, OHLCV, `{{plot_0}}` and `{{plot("Title")}}` substitutions. Named conditions and order fills accept a message override; `alert()` calls always retain their dynamic script messages. The existing notification, webhook, trigger-log, expiration, pause/resume and excessive-trigger controls apply. Script failures stop the subscription and display the actual error; they do not manufacture a signal. Replay and chart-study events alone do not create managed subscriptions.

## Strategy order executions

`scripts/pinets-alert-patch.mjs` adds source-checked hooks at native successful broker executions: entries/orders, reversal closes, normal and immediate closes, partial/bracket/trailing exits, risk close-outs and margin calls. The native ledger, sizing, margin and cancellation logic remain authoritative. A fill is emitted at the actual broker mutation; it is not inferred from a final net position or from an order being placed. `disable_alert` suppresses its event. Profit/loss/trailing messages and comments select the executed leg.

The live adapter retains the native broker ledger between observations while Pine variables retain the runtime's rollback rules. A pending market order works from the next observed price. Live pending orders evaluate that point rather than revisiting an earlier high/low of the forming bar. Confirmed `process_orders_on_close` executions and explicit `immediately` closes use the native close processor. Default close-only scripts can therefore receive intrabar order-fill events without enabling every-tick script calculations.

Fill events use an independent identity gate, allowing several fills in one bar without consuming an `alert()` call's frequency gate. Identity, structured fill metadata, event and rate counter commit together. Fill messages support `strategy.order.action/contracts/price/id/comment/alert_message`, `strategy.position_size`, `strategy.market_position`, `strategy.market_position_size`, `strategy.prev_market_position` and `strategy.prev_market_position_size`. `//@strategy_alert_message` populates the initial message; the default is action, contracts, ticker and fill price. Inserting `strategy.order.alert_message` does not recursively expand placeholders inside that argument. Combined subscriptions retain the script's own `alert()` messages.

These are **broker-emulator** executions. The UI, notifications and structured webhook payload (`execution: strategy_emulator`) identify them. Automated tests use real PineTS calculations, not a connected broker account. This feature places no exchange orders.

Remaining execution boundaries matter: PineTS currently captures order alert-message arguments when the order is issued or modified; arbitrary expression re-evaluation at fill time is not established. Exact native rollback/recalculation equivalence, all session boundaries, gap/trailing conventions and missing/unobserved market ticks remain comparison targets. The local server's 15-second observations cannot establish tick-by-tick execution equivalence.

## Recovery journal

Every saved subscription records the actual input observations, observation clock, candle deltas and ordered secondary-series replies. A persisted random seed makes runtime randomness reproducible. After a browser reload or Node process restart, a fresh isolated interpreter replays those exact inputs and verifies a SHA-256 digest of each input/output pair. This rebuilds Pine variables, intrabar `varip`, collections, the native broker ledger and pending orders, including positions created only during observed live ticks. Recovery never fetches replacement secondary history. It does not reconstruct ticks that the application never observed.

The browser worker commits observations in IndexedDB before returning their results. The browser then writes the accepted events, gates, rolling counters and cursor together in one Zustand persistence operation, followed by a journal acknowledgement. The Node evaluator uses separate atomic JSON journals in `.data/pine-recovery`, then an atomic alert-state transaction and acknowledgement. An interrupted acknowledgement cannot repeat a committed event. If the primary transaction was interrupted, replay regenerates its pending results with their original clocks and identities. Clearing the visible log does not clear the delivery cursor. Toast, audio and external notification delivery across a crash are not an exactly-once transaction with local storage.

Pause/resume retains the run identity and restores its previous observed state. Paused time contributes no observations. **Save changes** or an explicit whole-alert restart begins a new run; a member-only restart resets only stopped members. Exchange and simulation use separate journals and cursors. The first observation of a new source warms its own context; returning to a previously observed source restores that source's own run without borrowing simulated positions.

Missing journals, a journal older than its committed cursor, changed runtime/definition, input/output verification failures and storage failures stop the subscription visibly. Old evidence is retained where available. The application does not silently replace that state with a recalculated live position. An explicit restart is required to discard the previous run. Script inspection does not create a recovery journal.

Subscriptions created before this journal feature receive a run identity when first evaluated after the upgrade. Their existing gates/logs are retained, but observations that were never recorded cannot be recovered; their first journal begins with a fresh historical warm-up. Subsequent reloads recover the recorded run.

Storage is bounded at **64 MiB or 1,000,000 observations per stream**, and **256 MiB of current primary journals per browser origin or Node data directory**. Recovery admits at most **128 uncommitted observation batches**; a substantially older alert-state backup may need its matching journals or an explicit restart. Replaying a long run takes time, yields between batches and displays progress. Capacity exhaustion stops the alert before notification instead of silently truncating its run. Node `.bak` and up to 14 dated snapshots per journal are additional disk usage outside the primary-journal budget.

Keep browser site data and the Node data directory to retain recovery. Workspace export/sync contains definitions, gates and cursors, **not the IndexedDB/server observation journals**. Importing a cursor on another device without its matching journal stops that run and requires an explicit restart. Ordinary pause/resume and local cold restart are covered; portable runtime backup is not implemented. [Browser alert ownership](browser-alert-ownership.md) now elects one main tab per local origin and restores the journal before a waiting tab continues execution. Old generation results are rejected and the previous worker is terminated before handoff. Concurrent journal writes remain guarded as a second check. Popouts do not evaluate alerts. All main tabs must run the current build. The Node repository assumes one evaluator process; cross-device ownership, hosted failover and power-loss durability have not been established.

## Chart context and data boundaries

Time-based candles and visual styles using the same OHLCV are supported. Heikin-Ashi subscriptions transform the frozen context's actual candles and expose `chart.is_heikinashi`; messages use those synthetic OHLC values. Renko, range, Kagi, line-break and Point & Figure subscriptions are explicitly rejected until their construction settings and source mapping are implemented. Tick intervals are also rejected.

`request.security()` uses the controlled market provider and imports use only the saved library bodies. Unavailable secondary data raises a visible error. This does not establish complete `request.*` or Pine API equivalence; order-flow requests, all placeholder types and every nonstandard ticker modifier remain outstanding. Primitive input metadata is supported; this does not establish every native input type or study visual equivalence.

Browser subscriptions need an open main tab. The server observes provider snapshots every 15 seconds; it cannot recover every intervening tick, and duplicate OHLCV snapshots do not simulate ticks. It uses the existing Binance, Hyperliquid and Yahoo adapters; Yahoo is delayed and exchange history limits still apply. The source is labeled when simulated. Browser candle watchlists currently cover the first 40 members; the shared server planner loads at most 60 distinct primary series per pass. These are explicit capacity limits, not full-universe or hosted-service parity.

Exchange/simulation boundaries invalidate queued results from the preceding source and select the corresponding recovery journal. Intrabar variables and positions never cross between sources; frequency and excessive-trigger gates remain durable. Notification toasts label simulated signals.

## Interpreter boundaries

The interpreter exposes JSON series and timezone-formatting bridges, with no Node, DOM, network, storage or host object references. Every context has a 128 MiB memory limit, a 1 MiB stack limit, a 5-second observation deadline, a 100,000-loop runtime limit and at most 40 secondary requests per observation. History is limited to 20,000 bars, output to 500,000 characters and raw signals to 100 per observation. The browser worker queue admits at most 128 pending observations; exceeding a budget stops the script visibly. This isolation is not a hosted multi-tenant security audit or a capacity/load guarantee.

## Verification and references

`tests/pine-alert-runtime.test.ts` executes the actual PineTS bundle in QuickJS, including imported libraries, frozen inputs, secondary series, `varip`, close frequencies, Heikin-Ashi, strategy timing and interpreter isolation/deadlines. `tests/pine-alert-rules.test.ts` checks message expansion, persisted frequency gates and backup validation. `tests/pine-alert-server.test.ts` exercises JSON persistence/restart, real Pine execution, multiple calls, watchlist isolation/rate stops, script errors and a pause while secondary data is pending.

`tests/pine-order-fills.test.ts` additionally exercises native next-observation markets, stops, successful profit/loss/trailing legs, partial closes, reversals, immediate round trips, close-only fills, fill recalculation, risk close-outs, cancellations and alert suppression. Server tests cover all three strategy event selections and authenticated forwarding of structured emulator fills in actual HMAC-signed payloads. Browser-store tests rehydrate the persisted fill gate together with the event and rolling rate state.

`tests/pine-journal.test.ts` runs the actual interpreter through JSON journal recovery: live positions/brackets, pending markets, random sequences, collections, exact secondary replies, older consumer cursors, corrupt evidence and cancellation. `tests/pine-journal-db.test.ts` exercises IndexedDB transactions with fake-indexeddb, including concurrent writes, quota rollback and scoped cleanup. Server tests perform genuine module reloads against temporary JSON directories and inject failures between journal, event-state and acknowledgement writes. Missing/corrupt journals stop visibly. Store tests verify atomic batch/cursor persistence and duplicate suppression after clearing display logs.

The snapshot and user-created-subscription behavior follows the documented [TradingView alert model](https://www.tradingview.com/pine-script-docs/faq/alerts/). Script call frequencies and named conditions are described in the [Pine alerts documentation](https://www.tradingview.com/pine-script-docs/concepts/alerts/); realtime variable behavior is described in the [execution model](https://www.tradingview.com/pine-script-docs/language/execution-model/). Those references define the comparison target, not proof of complete equivalence. The interpreter uses [quickjs-emscripten](https://github.com/justjake/quickjs-emscripten).

The strategy comparison target is documented in [Strategy Alerts](https://www.tradingview.com/support/solutions/43000481368-strategy-alerts/), [strategy alert concepts](https://www.tradingview.com/pine-script-docs/concepts/alerts/#order-fill-events) and [message placeholders](https://www.tradingview.com/support/solutions/43000531021-how-to-use-a-variable-value-in-alert/). Native/reference timing beyond the explicitly tested behaviors remains unproven.

Browser persistence follows the documented IndexedDB [transaction durability options](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction) and [transaction completion event](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event). Where strict durability is unavailable, the browser's default transaction durability is used; storage retention remains subject to the browser and available disk space.

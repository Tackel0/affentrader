# Movement alert operators

Implemented and checked on 2026-10-25. The condition builder now exposes Moving up, Moving down, Moving up % and Moving down % for candle sources and the output lines of the shared technical-indicator catalog. They are available in indicator, combined and watchlist rules, with the existing frequency, expiration, server execution and notification controls.

## Calculation and data contract

For a selected source `s`, the current value is compared with `s[N]`, its value N actual bars ago. Absolute movement is `current - reference`; percentage movement is `100 * (current - reference) / abs(reference)`. Up meets a positive threshold and Down meets its negative, including equality. Negative oscillator values therefore retain their numerical direction. A zero percentage reference is unavailable, while zero remains valid for absolute movement. Amounts must be finite and positive, and N must be a whole number from 1 through 19,999.

The source can be open, high, low, close, hl2, hlc3, ohlc4 or candle volume, or a selected shared study output such as EMA, RSI, MACD signal or histogram. Absolute units follow the source: price currency, base volume or indicator points. The UI excludes constants, drawn lines and provider snapshot metrics because they do not supply this candle-aligned source history. Provider change percent remains a separate legacy condition.

Both endpoints must be finite. Missing lookback, indicator warm-up, zero percentage baseline and overflowing arithmetic leave the condition unavailable; an established transition state is retained across the gap. Timeframe overrides and other-market leaves use that market's actual source history. Tick intervals count actual collected tick bars, not elapsed nominal minutes; their synthetic grid identifiers may advance beyond wall time and are retained as collected observations. Time-based future bars are excluded at the runtime evaluation clock. Bar-close mode uses the confirmed candle view, so neither a later live candle nor a live quote replaces the confirmed reference/current values.

The history planner now requests at least N + 2 candles, plus conservative indicator warm-up before the reference. Shared (symbol, interval) dependencies load only their deepest requested history. Editing to a larger lookback upgrades an already prepared series. The server's exchange adapters accept the requested count rather than always loading 300 bars; the short cache upgrades for a deeper request, reuses a sufficiently deep fresh series for smaller requests, and is bounded to 128 series. Requests retain the common 20,000-bar limit and the venues' actual history availability. If a venue cannot supply the reference, the rule remains unavailable rather than shortening the requested lookback.

## Fidelity boundary

The primary [TradingView alert-configuration guide](https://www.tradingview.com/support/solutions/43000763312-learn-how-to-configure-alerts/) documents the four operators and their amount/bar controls. Its prose does not specify all internal sampling, reference-window, negative-source and warm-up details. This implementation uses the explicit N-bar source comparison described above; exact equivalence to TradingView's internal movement evaluator has not been established by a side-by-side native-alert test. That remains a parity requirement rather than an assumed result.

Subsequent work implemented [excessive-trigger stops and independent member recovery](alert-rate-limits.md). Other open alert work includes full-universe candle capacity (browser preparation currently 40 watchlist members; server loads 60 series per pass), exact exchange-session calendars, inactivity expiration, continuously observed server ticks and hosted redundant delivery. The 15-second local server poll and upstream cache limits remain in force. These checks do not assert a real external webhook/push delivery.

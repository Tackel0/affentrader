# Shared paper trading and local Replay

The live paper account is shared by this browser's cooperating tabs. One main tab owns live order matching through an exclusive Web Lock. Other tabs, including popouts, can enter, cancel and close orders using the same serialized account-write queue. Closing or navigating away from the matcher lets a waiting main tab take over after loading the durable account. The Paper and DOM panels show the current matching role; a failed matcher exposes a retry action in the Paper panel.

Only simulated account values change. There is no real broker connection or exchange order submission.

### Matching access diagnostics

The Paper panel distinguishes waiting for exclusive access, preparing shared storage, running in this tab, stopped locally and failed. Standby no longer claims another main tab is processing fills: a held browser lock proves access ownership, not execution activity. **Matching details** reads a fresh Web Locks query on demand and shows held/pending execution and write-lock counts. It also counts distinct browser contexts and whether the holder has a pending request itself, without displaying or persisting client identifiers. An unavailable query is reported, not replaced by invented counts. Snapshots remain labeled and can be refreshed or hidden.

The 2026-10-26 production inspection found one held execution lock, two pending requests and three distinct browser contexts; both inspected tabs were waiting at generation zero and the holder was not also waiting. No account-write lock was held. Thus a third context held access; this does not identify its tab, establish its activity or authorize terminating it. No lock was stolen or timed out. Local retries only stop/restart this tab's own lease; they do not revoke another holder. Existing frozen-owner and hosted-execution limits still apply.

The [Web Locks specification's query semantics](https://w3c.github.io/web-locks/#api-lockmanager-query) define client identifiers per frame/worker context and warn that a returned snapshot may already differ from current state. Aggregated context counts are unavailable when the browser omits identifiers; the application does not substitute the number of lock requests for the number of contexts.

`matching-access.test.ts` covers counts, identifier privacy, missing query support, failures, empty snapshots, same-context versus separate-context requests and the real lease's waiting/preparation/running/cancel/failure phases. Existing ownership tests retain exclusivity and epoch checks.

## Account writes and quotes

`editLivePaper` refreshes a newer persisted account while holding the origin-wide write lock. A command buffers its changes and publishes one complete snapshot. It restores its previous in-memory state on validation or storage failure. A stale tab therefore cannot overwrite a fill, accepted cancellation or another order. Order and fill identifiers are generated from the latest account sequence. Protective brackets use the existing OCO broker path; an already-filled order cannot be turned back into a canceled order by a later stale command.

Quotes are observed locally in every tab for ticket prices and P&L displays. They do not write an older account back to storage. The elected matcher processes delivered samples through a bounded FIFO, retaining intervening up/down transitions rather than coalescing everything to the last price. It persists bounded batches under the same lock as user commands. A failed write, invalid stored account or overflowing queue stops that matcher visibly. Generation checks prevent a previous holder's queued batch from committing after handoff.

Live fill time is the browser's sample-receipt time. Samples received before an order's accepted timestamp are ineligible to fill it later while waiting in a queue. This is a millisecond browser clock and a sampled public-data simulation, not a reconstruction of exchange queue position or exact exchange execution chronology. Limit fills, stops, fees and slippage retain the local broker's documented simplified model. A close rejected for a missing quote retains its protective working orders.

The persisted account is validated before reading and committing. Unsupported future storage versions and removed/corrupt storage are retained or left removed, rather than replaced by an empty account from an older tab. Reload after deliberately removing account storage. Account reset remains an explicit user action in the UI. Nonfinite numeric order inputs are rejected and sanitized in rejected-order history.

## Replay isolation

### Reverse position

Reverse is available in the positions table, DOM and a position strip in each chart legend. It submits a single opposite market order for twice the current quantity, closing the old exposure and opening the same size in the opposite direction. This matches the quantity contract in TradingView's [Reverse position help](https://www.tradingview.com/support/solutions/43000754950-reverse-position/) and [position API documentation](https://www.tradingview.com/charting-library-docs/latest/trading_terminal/trading-concepts/positions/), checked 2026-10-26. The controls are in the chart legend; exact native price-line control placement/settings parity is not claimed.

The pure broker first computes an isolated candidate using executable bid/ask or the existing last/bar model, full double-quantity fees and configured slippage. It then checks the complete resulting account's margin against its equity, including other markets and the reversed position's liquidation mark. Insufficient/nonfinite capital or a missing quote rejects the action while retaining the original cash, fills, position and protective orders. An accepted reversal cancels working reduce-only exits on that symbol, retains unrelated entry orders and other markets, and creates no new bracket automatically. This protection policy is explicit local behavior, not verified equivalence for every native broker.

The shared command captures the position's quantity, entry and opening time at dispatch and rechecks those fields after acquiring the account-write lock. A changed position requires review instead of silently reversing a different exposure. A single durable snapshot commits the reversal and protective cancellations; a storage failure rolls everything back. Per-control busy guards prevent repeated clicks while pending. Chart controls activate their own cell and reject another chart's Replay context. Replay reversal uses its historical clock and ephemeral account, never the durable live account.

The chart position strip and primary position overlay use the same liquidation-side marks as the table. Open-position overlay marks expire on a one-second refresh even when no further quote arrives. Native non-time styles, exchange queue/liquidity, partial fills, contract multipliers, FX settlement and full native position-management equivalence remain outside this model.

`position-reversal.test.ts` checks both directions, exact double quantity, fees/slippage, realized/new exposure arithmetic, post-reversal capital, missing quotes, tiny legacy exposure, unrelated orders and protected rejection. Additional actual store/write-lock tests cover atomic persistence, changed-position rejection, quota rollback and Replay isolation. Production browser evidence is recorded in `artifacts/verification.md`.

Each tab has its own ephemeral Replay account, price map, observation clock and preceding bar samples. Replay orders and fills never enter the shared live account. An elected tab can display Replay while its background matcher continues processing the shared account's live orders. Other tabs retain their own live/Replay selection. Hydrating a newer live account preserves the local Replay position, mode, price map and ticket.

Each native Replay start or seek opens a fresh Replay account with the live account's starting-balance, fee, slippage and leverage settings. The already revealed cursor bar seeds its historical price and clock. A queued command is rejected if its selected account context changes while it waits, even if the tab switches back to Live before the lock is granted.

Replay order acceptance uses the current historical bar time. Repeated updates to one forming bar visit only movement after the preceding observation: its new close and any newly extended high or low. They do not reuse old extrema to fill an order placed later in that bar. Older bar updates are ignored, and a native seek resets the local session. When an entire bar is revealed at once, matching still uses the local OHLC path convention; the order of unobserved intrabar trades is not known. This differs from a tick-complete native broker emulator.

## Execution price provenance

Order acceptance and fill provenance are stored separately. The source of the actual matching observation labels each fill, including marketable limit/stop orders, stop-limit execution, bracket exits and explicit closes. A working order accepted on a market quote can therefore later fill on a synthetic observation, or the reverse. Brackets inherit their creation source from the entry fill; each protective fill still records its own matching source. All these are simulated paper transactions, including those labeled **Market feed**. That label describes the public price input, not a real broker execution.

The order ticket and DOM identify their local price source. Order history and Trades retain **Market feed**, **Offline simulation**, **Replay**, or **Replay · synthetic**. Historical records without metadata remain **Not recorded**. The application never infers a missing fill source from an order's acceptance source. A feed restart clears local paper quote caches and invalidates queued ticket commands and matching batches from the former feed generation. A market order then needs a fresh observation.

Explicit **Simulation** mode generates labeled synthetic history, trades and quote-only updates for Binance, Hyperliquid and Yahoo identifiers. It rejects late real observations and makes no provider requests. The last observed price seeds the artificial path; a tab-local saved seed survives reload. When no market observation or saved anchor exists, the symbol's configured seed is used (unknown external symbols use 1). This seed is an artificial starting level, not a verified valuation. Generated time/tick bars and Replay derived from them stay synthetic. Simulation does not fabricate an exchange order book. Automatic Hyperliquid/Yahoo outages remain unavailable; Binance retains its explicitly labeled automatic offline fallback.

Feed generation changes recreate the primary native chart session, matching the existing satellite-chart lifecycle. Vela 0.9's depth-only `setMarket({ bars })` path extends the former series instead of replacing it, so it cannot represent a provider/source restart. A fresh session restores saved drawings, studies and display settings over the new history without joining old and new source bars. An active native Replay ends when its feed session is replaced.

When multiple tabs select different feed modes, the elected matcher determines the source used for shared working orders. Immediate marketable orders and explicit closes use the submitting tab's locally observed price. Fill metadata records that distinction; selecting Simulation in a standby tab does not change the primary tab's feed or working-order matching source.

## Reviewed full and partial position closes

With instant paper placement disabled, Close in the chart legend/positions table and Flatten in the DOM open a close dialog. It previews the market side, remaining exposure, estimated execution with configured slippage, exit fee and realized P&L excluding the already paid entry fee. Partial close accepts a quantity within the captured exposure, with 25/50/75/100% shortcuts. Invalid, oversized and quantities below engine precision cannot be submitted. When instant placement is enabled, Close retains immediate full-close behavior. This follows the interaction described in TradingView's [partial-close help](https://www.tradingview.com/support/solutions/43000703856-how-to-make-a-partial-close/) and [order-placement help](https://www.tradingview.com/support/solutions/43000786671-how-to-place-an-order-on-tradingview/), checked 2026-10-26; exact broker equivalence remains unproven.

The quote preview remains indicative: the serialized command resolves the currently eligible quote when it executes. It captures symbol, account mode/generation and position quantity, average entry, opening time and realized P&L, then rechecks these after loading the latest shared account. A changed position or account requires reopening the dialog. Storage failure rolls back the fill and protection changes together.

A partial close keeps the remaining position's entry basis and opening time, retains unrelated working entry orders and caps oversized same-symbol protective exits at the actual remaining exposure. Smaller protective quantities stay unchanged. Resized orders increment revision and modification provenance so old editors cannot overwrite them. A successful full close cancels this symbol's working orders; a rejected close preserves them. This is the local protection policy rather than verified equivalence for all native broker accounts. Partial position close is a user-requested smaller market order, not exchange-liquidity partial fills; the latter remain unmodeled.

`partial-close.test.ts` verifies long/short arithmetic, executable sides, fees/slippage, quantity/precision rejection, protective revisions, OCO follow-up execution, unrelated orders and rejected/full closes. Actual store tests verify one durable write, quota rollback, stale shared position reviews, symbol/context collisions and Replay isolation. Desktop production Replay checks cover chart, table and DOM dialogs, oversized-input rejection, 50% close, resized protection and final full close. Live-browser execution with an active matching owner, instant-close UI flow and every mobile/satellite layout remain unverified.

## Working order modifications

### Direct order-line controls

A dedicated Vela renderer layer paints working order lines and places keyboard-accessible edit/cancel controls at their projected prices. It runs per mounted chart, filters by the cell's symbol and local Live/Replay context, follows scale/zoom/resize frames and cleans up its DOM/subscription when destroyed. Store-only account changes coalesce to one animation frame; quote-only changes do not independently rebuild controls. Visible labels pack within the price pane, with leaders retaining the exact underlying price coordinate. Out-of-view levels and labels exceeding available pane height remain accessible through the legend's order list. Narrow cells constrain label width; exact native collision/layout parity is unproven.

Click a price/quantity label or activate it with the keyboard to open the existing modification dialog. Vertical dragging uses Vela's inverse scale projection from the original price coordinate, including log/inverted scales, and seeds only that price field in a review dialog. Canceling the dialog leaves the order unchanged; saving uses the existing revision, account-context, buying-power and storage guards. A stop-limit exposes both trigger and limit before activation, then only the remaining limit after triggering. The line's cancel button checks revision and captured account context inside the serialized write before canceling, with quota rollback. There is no automatic exchange tick-size snapping in this paper model.

Production desktop Replay verifies line clicks, price editing, drag-and-cancel, drag-and-save on the limit leg of a stop-limit, separate stop/limit labels, and cancellation through either leg. The final six live fills remain unchanged in two tabs. Geometry tests cover filtering, phases, invalid levels, label packing/capacity and arbitrary inverted/log projections; actual store tests cover cancellation revisions, context collisions and failed writes. Satellite and narrow-cell wiring is implemented, but interactive dragging in every mobile/multi-chart layout remains unverified. Primary-chart PNG labels now have a visually verified canvas counterpart; see [chart snapshots](chart-snapshots.md). Complete workspace export and exact DOM/raster font equivalence remain open.

Working limit, stop and stop-limit orders can be modified from the Orders table, chart legend or DOM. The editor changes quantity, the applicable prices and optional entry brackets; symbol, side and order type remain fixed. Saving a marketable amendment can execute immediately against the current eligible quote. Protective exits cannot acquire nested brackets, and changing their quantity updates working OCO siblings together. A triggered stop-limit retains its triggered phase and cannot change its trigger.

An amendment retains order identity and acceptance metadata, increments its revision and records modification time/source. The editor captures revision and account context; changed orders, completed orders and a changed Live/Replay context require reopening. Validation, capital checks and storage failure leave the original account intact. A no-op save performs no durable write or matching. Immediate execution considers only the amended order, and previously queued observations cannot fill an order amended after their receipt time. This uses millisecond browser timestamps, without claiming exchange-level ordering within one millisecond.

Reduce-only execution rechecks current exposure, trims excess quantity to the remaining position and cancels protection when there is no opposite exposure to reduce. This prevents an older protective quantity from opening a reverse position after a partial close. Tests cover pure broker behavior and actual serialized store commands, including quota rollback, stale editors and isolated Replay amendments. Production browser evidence verifies order identity, invalid-input rejection, marketable execution, OCO quantity updates and chart/table/DOM entry points in Replay. Live-browser amendment under an active shared matcher, partial fills and complete native broker equivalence remain unverified.

## Order tickets

### Bid/ask execution and marks

Fresh public depth now supplies executable sides: buy at ask, sell at bid, including explicit closes. The configured adverse slippage is applied afterward to market/stop fills. An order book must match the symbol and public/synthetic price source, contain positive nonempty levels, have bid no greater than ask, and be no more than ten seconds old or ahead of the browser observation clock. Best prices are selected independently of depth sorting. The service publishes depth for all already subscribed chart/account markets, without replacing the main chart's depth with another market. This does not add unlimited background depth subscriptions.

Reference checked 2026-10-26: TradingView's [paper P&L explanation](https://www.tradingview.com/support/solutions/43000719857-how-is-position-profit-and-loss-in-paper-trading-calculated/) and [market-order help](https://www.tradingview.com/support/solutions/43000754940-what-is-a-market-order/) describe these executable and liquidation sides. Their complete broker/service behavior is not reproduced by this sampled local model.

The ticket displays side prices and spread, or explicitly identifies the last-price / historical-bar model when usable depth is absent. There is no invented bid/ask spread. Resting buy limits need ask at or below their limit, sell limits need bid at or above; they retain the local model's limit-price fill. Immediately marketable limits improve to the executable side. Stops trigger against observed last prices and execute against bid/ask; triggered stop-limits still wait for the correct executable side. This is a documented local trigger policy, not proof of exact native stop semantics across asset classes.

Long positions mark to bid and shorts to ask while matching fresh depth is available; account and position displays otherwise use the observed last price. Account equity samples use these liquidation marks when a command or matching observation is processed. Expiry updates the visible ticket/marks on a one-second timer; it does not manufacture market observations or periodic durable equity samples during a feed outage. The account model remains USDT-based, without automatic currency conversion or contract point values.

Matching observations capture their executable quote before entering the shared FIFO. A queued old observation cannot read a newer book to fill retroactively. Live commands resolve depth inside their serialized command. Source switches clear book caches, and Replay never uses live depth. A fill records **Bid**, **Ask**, **Limit**, or **Last / bar** separately from its price-feed provenance. Existing fills without this field remain **Not recorded**. A bid/ask basis precedes configured slippage; it does not assert execution exactly at displayed bid/ask after that adjustment.

`paper-bid-ask.test.ts` exercises the actual pure broker, depth eligibility, spread round trips, shorts, slippage, limits, stops, stop-limits, source separation, liquidation marks and legacy validation. Actual store/lock tests cover placement, durable hydration, queue snapshots and Replay separation; the Hyperliquid service test covers background depth observers and unsubscription. Public book prices are sampled liquidity indications: fills still assume the full order quantity, without depth consumption, queue priority, partial fills, venue routing or liquidity guarantees. Full native execution parity remains open.

Tickets are per tab and saved in session storage across reloads. The first load adopts an earlier shared ticket preference when present. Ticket edits, quote display and Replay operations cannot publish a shared account snapshot. The shared paper account's older saved `ticket` property is read for migration but excluded from subsequent account writes. A newly opened independent tab can therefore have its own ticket quantity and order type.

`paper-concurrency.test.ts` loads actual independent Zustand modules against one backing store and lock manager. It covers preserved simultaneous commands, unique fills/ids, duplicate samples, OCO cancellation, acknowledged cancellation versus fills, quote/ticket write isolation, live matching during Replay, hydration, quota rollback, storage-version/removal safeguards, selected-context changes, actual ownership handoff and stale-generation rejection. Replay cases cover historical order times, same-bar extrema, older bars, resets and ticket migration.

Additional `broker.test.ts` cases cover protection after a rejected close and nonfinite input history. Production two-tab and native Replay checks are recorded in `artifacts/verification.md`.

`paper-execution-source.test.ts` covers source-aware immediate and queued broker paths, source transitions, legacy records and validation. Actual-store concurrency cases additionally cover durable source metadata, fresh observations after feed changes, obsolete queued ticket commands and synthetic Replay isolation. `market-simulation.test.ts` exercises explicit multi-provider ticks/history, saved anchors, rejection of late real samples and the absence of synthetic Hyperliquid/Yahoo fallback in automatic mode.

All participating tabs need the current build and HTTPS or localhost with Web Locks support. Separate browser profiles/devices do not share these locks or a paper account. A frozen owner can delay matching until it leaves; locks are not forcibly stolen. Matching requires an open eligible main tab and delivered prices. There is no hosted execution while all main tabs are closed, recovery of unobserved ticks, multi-currency settlement, contract/tick/lot metadata model, borrowing/funding/liquidation model or real broker connectivity. The current virtual account is denominated in USDT; displayed market quote currencies are not automatically converted into that settlement currency. Full TradingView paper/broker equivalence remains outstanding.

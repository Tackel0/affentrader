# Entry-order exit levels

The paper order ticket's **Configure exit levels** action prepares up to four independently sized exits before entry. The same editor is available from **Modify order** for a working entry. One level may contain only TP or SL; multiple levels require both legs per pair. Configured quantities may cover part or all of the order but cannot exceed its quantity beyond floating-point rounding tolerance. The ordinary TP/SL fields remain available when multi-level configuration is cleared.

**Apply exit levels** updates the local ticket or the modification draft; it does not submit an entry or save a working-order amendment. The portal form stops submission propagation, and the outer ticket accepts submission only from its own form. **Buy/Sell** or **Save modification** performs the account operation separately. The editor captures its ticket/order/account context, preventing application to a changed symbol, side, quantity, order type, revision or account generation. Live quote changes do not discard a draft; entry-side prices are validated again by the broker at submission.

Pending entry orders persist their exit definitions without creating active protective orders. On fill, the actual matching source/time stamps each new child. Every level has its own OCO group, so one exit cancels only its paired sibling. Later groups remain available for the rest of the exposure. Arrays are copied before a shared command waits for the write lock and again when accepted into broker state, preventing caller mutation from changing an already submitted configuration.

The engine validates positive finite quantities/prices, four-level limits, paired multi-level exits, total quantity and entry-side TP/SL directions. Regular bracket fields cannot coexist with populated exit levels; reduce-only exits cannot carry nested exit definitions. Changing a working entry's quantity below its configured coverage rejects the amendment without altering the original. Clearing levels is explicit and identical saves remain no-ops.

The paper engine uses one net position per symbol. When an entry offsets an opposite position, new child quantities are capped in configured order at the exposure remaining in the entry's direction. An order that only reduces or flattens an opposite position creates no orphan children. This is local net-position behavior; independent hedged positions, broker reservation semantics and complete native exchange equivalence remain unverified. Existing limit/stop fill, gap and intrabar-path conventions remain unchanged; activating children does not reconstruct unavailable exchange ticks or add liquidity-dependent partial fills.

The ticket remains per-tab session data, including temporarily over-covered drafts after quantity edits, so reload does not silently discard the configuration. Draft structure is validated separately from account submission. A fresh chart Buy/Sell ticket clears old entry levels; selecting reduce-only also clears them. Image/workspace preferences do not publish ticket data as a shared paper-account write.

The durable account envelope now writes **version 1**, under the existing account-write transaction, and reads legacy version 0/unversioned accounts without an eager write. The prior reader rejects nonzero envelope versions, fencing cooperative older builds before they can match or edit new-format accounts. Reload those tabs with this build. This prevents an older matcher from silently ignoring exit definitions; it does not guarantee availability of a frozen lock holder or prove every old/external client cooperates. Unknown future versions remain rejected without replacing stored data.

The four-level interaction follows the previously inspected [TradingView multi-exit documentation](https://www.tradingview.com/support/solutions/43000772334-multiple-take-profit-and-stop-loss-levels/). Native preset integration, every mobile/layout interaction, hosted execution and exact order-type/broker equivalence remain open. Production Replay evidence and verification limits are recorded in `artifacts/verification.md`.
